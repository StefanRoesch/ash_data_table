# Architecture map

Read this file before a build. It says where things are, so that you do not have to read every guide and the whole drawing first. Paths are from the repository root. Line numbers are of stage 3c of the refactor (the live core); stage 4 moved the drawing into `lib/ash_data_table.ex`: each section says how to get them again.

The words used here (table, column, cell, picker, action panel, …) are defined in `CONTEXT.md`.

## The four parts

The extension has four parts. This is the target structure agreed with the owner; `docs/architecture/target.md` describes it, and its section 9 says which stages of the refactor are done. A file's directory says its part (target.md 5.5), and `test/architecture_test.exs` checks the direction of every dependency from it: it fails on what breaks the rules, and on any cycle inside the data layer (2a, since the finishing items of 2026-10-21).

| Part | What it is | Where it is today |
| --- | --- | --- |
| 1. Table declaration | The `table` and `tables` blocks of a resource, the `table` block of a domain, the checks at compile time, and the notifier of live updates. | `lib/ash_data_table/resource.ex`, `lib/ash_data_table/resource/**`, `lib/ash_data_table/domain.ex`, `lib/ash_data_table/domain/**` |

| 3. Table UI components | Markup and the browser hooks. | the kit (`lib/ash_data_table/kit.ex`, `AshDataTable.Kit`, the behaviour; `kit/default.ex`, `AshDataTable.Kit.Default`; `kit/projection.ex`, `AshDataTable.Kit.Projection`, what each part is given to draw, with one module per outer part in `kit/projection/`), `lib/ash_data_table/parts/*.ex` (`AshDataTable.Parts.*`, the internals of `Kit.Default`), `attrs.ex` (the bundles and the markup contract), the five hooks in `assets/js/` (JS files of the package; the colocated hooks of `AshDataTable` import them), the behaviour `lib/ash_data_table/component.ex` and the shipped components in `lib/ash_data_table/components/` |

Ready-made wiring | The public entry, the router line, the page and the tag's live component that connect 2 and 3. | `lib/ash_data_table.ex` (`table/1`, `attach/4`, `detach/2`, `attached/1` and the five colocated hooks), `lib/ash_data_table/live/drawing.ex` (`AshDataTable.Live.Drawing`, which calls the kit's parts with what the core holds), `lib/ash_data_table/router.ex`, `lib/ash_data_table/live/page.ex`, `not_found_error.ex`, and `live/embedded.ex` (`AshDataTable.Live.Embedded`, what the tag renders: its callbacks hand the socket to `Live.Core`, it draws with `attached/1`) |

A table reaches a page in three ways, all on one live core and one drawing (stage 4), through one kit (stage 7b): the router line (`Live.Page`, which attaches its table), the tag (`<AshDataTable.table>`, one live component, `Live.Embedded`), and `AshDataTable.attach/4` in a host's LiveView, drawn with `AshDataTable.attached/1`. `attached/1` draws every table of the page, nested tables and pickers' tables included, from one registry (`Live.Registry`). There is exactly one `live_component` in `lib/`: the tag's.

## Module map

One line per module. The functions named are the ones other modules call.

### Part 1: declaration

- `AshDataTable.Resource` (`resource.ex`): the Spark extension. Defines the entities (`@column`, `@ask`, `@relationship`, `@argument`, `@reference`, `@action`, `@upload`), the sections `@table` and `@tables`, the named table entity `@named_table`, and the list of verifiers at the end.
- `AshDataTable.Resource.Table` (`resource/table.ex`): one table as written. `options/0` is the option schema that the `table` block and a named table share. `path/1`, `anno/2`, `option_anno/3` find where an error points to. `in_words/1` names the table in a message.
- `AshDataTable.Resource.Column`, `.Ask`, `.Relationship`, `.Action`, `.Reference`, `.PageArgument`, `.Argument`, `.Upload` (`resource/*.ex`): the structs of the entities, each with `schema/0`. `page_argument` (inside `action`) names a public argument the page fills.
- `AshDataTable.Resource.Info` (`resource/info.ex`): read a declaration. `tables/1`, `table/2`, `table!/2`, `no_table/2`; for the default table `columns/1`, `relationships/1`, `actions/1`, `arguments/1`, `uploads/1` and the generated `table_*` functions.
- `AshDataTable.Domain` and `AshDataTable.Domain.Info`: the domain's `table` block (`authorize?`, `scope_assign`, `actor_assign`, `tenant_assign`, `time_zone_assign`, `pub_sub`). `Info.authorize?/1`, `Info.reader/2`, `Info.assign_names/1`, `Info.time_zone/2`, `Info.time_zone_assign/1`, `Info.pub_sub/1`. Its one verifier, `Domain.Verifiers.VerifyPubSub` (`domain/verifiers/`), reports a domain that names no `pub_sub` and has a resource that says `live? true`.
- `AshDataTable.Resource.Transformers.Announce` (`resource/transformers/announce.ex`): the extension's one transformer. It gives a resource that says `live? true` the notifier `AshDataTable.Resource.Notifier`, named as an atom.
- `AshDataTable.Resource.Notifier` (`resource/notifier.ex`): the notifier of live updates (see "Live updates" below). `topic/2`.
- `AshDataTable.Resource.CellType` (`resource/cell_type.ex`): Ash type to cell type. `of/2`, `classify/2`.
- `AshDataTable.Resource.Operator` (`resource/operator.ex`): filter operators per cell type. `available/2`, `to_ash/2`; `takes/1` (no value, one, several, a range), `predicates/2`, `negated?/1`.
- `AshDataTable.Resource.Words` (`resource/words.ex`): `humanize/1`, a name in words.
- `Mix.Tasks.AshDataTable.Install` (`lib/mix/tasks/ash_data_table.install.ex`): the Igniter installer.

The rules of a declaration live in one module per topic. Each is shared by the verifiers (which report a mistake) and the model (which builds on the answer). Most return `{:error, reason}` and turn the reason into text with `message/1`.

- `Resource.Reading`: read action, pagination strategy, page sizes, what can be sorted. `read_action/2`, `strategy/2`, `page_sizes/2`, `sortable?/3`, `private_read/2`.
- `Resource.Editing`: the update action behind a column and whether it can serve an inline edit. `update_action/4`, `edit/4`, `editor/3`, `obstacle/2`.
- `Resource.Acting`: row actions, table actions, create, and their inputs. `offered/2` (also checks the `page_argument`s), `create_action/2`, `inputs/5` (without `record_argument` and the page arguments), `page_names/1`, `record_argument/3`, `bulk?/3`.
- `Resource.Arguing`: arguments of the read action and of calculation columns. `inputs/1`, `mistakes/3`, `declared_mistakes/2`.
- `Resource.Relating`: relationships a row offers and the nested table. `offered/2`, `declared/2`, `nested/1`, `read_action/2`, `public_read/2`, `page_sizes/2`.
- `Resource.Referencing`: reference cells, `label_field`, the picker, and `sticky_label?`. `label_field/1`, `sticky_label/2`, `reference/1`, `picking/2`, `declared/4`.
- `Resource.Managing`: arguments that a `manage_relationship` change hands to a relationship. `managed/3`, `handed/3`.
- `Resource.Embedding`: fields of a map cell, kinds of a union. `of/2`, `union/2`, `kind/2`. A value with a sensitive input, or a sensitive primary key, is read-only (its `obstacle`).
- `Resource.Presenting`: the `component` of a column, and how many lines its cells show (`max_lines`). `column/4`, `component/2`, `max_lines/3`.
- `Resource.Uploading`: limits of a file argument. `limits/2`, `mistakes/3`.
- `Resource.Exposing`: columns that show a field a field policy protects. `exposures/2`. Also whether a field is `sensitive?`: `sensitive?/1`, `typed?/1`, `empty?/1`.
- `Resource.Summarising`: the `summary` of a column (footer summaries). `column/2` (an attribute, not sensitive, a kind that fits the type), `action/1` (not a manual read action), `data_layer/2`, `fits?/2`.
- `Resource.Listening`: live updates. `announces?/1` (the resource says `live? true`), `follows?/2` (a table of it listens), `pub_sub/1`. Its findings are reported by the domain's verifier, not by a resource's.

Verifiers (`lib/ash_data_table/resource/verifiers/`), in the order `resource.ex` lists them: `VerifyTables` (names and duplicates in named tables), `VerifyReadAction`, `VerifyUpdateAction`, `VerifyLabelField` (also `sticky_label?`), `VerifyColumns`, `VerifyComponents`, `VerifyRelationships`, `VerifyActions`, `VerifyUploads`, `VerifyExposure` (warnings only), `VerifySummaries`.

A new diagnostic goes in two places. Put the rule and its `message/1` clause into the topic module above. Raise it from the verifier of that topic as a `Spark.Error.DslError`, with `Table.path/1` and `Table.anno/2` or `Table.option_anno/3` so that it points at the right line. A verifier checks every table of the resource: loop over `AshDataTable.Resource.Info.tables/1`. Then add it to `documentation/topics/mistakes-at-compile-time.md`.

### Part 2: internals

The model (2a):

- `AshDataTable.Model` (`model.ex`): everything a table is rendered from, built at runtime from `Ash.Resource.Info` and the declaration (ADR `docs/adr/0001-table-model-from-resource-info-not-manifest.md`). `build/2` builds it for a resource and a table name, the same for everybody. `for_actor/2` takes out the columns and actions this person can never see or use. `defaults/2` and `supply/2` fill in arguments. `bulk_actions/1`, `loads/1`, `relationship/2`, `summarised/1` (the columns with a `summary`), `keeps_one?/1`, `label/1` (what a resource's table is called, before it is translated). `group?/1` (a column or input edited as groups of fields, or a union), `in_panel?/1` (a column whose cells are edited in the side panel: an array, a map cell, a union), `input/2` (that column as the panel's one input), `filter_input/1` (the input of a filter's panel of several values). Its `sticky_label?` is the table's option of that name. `editing?` (a column can be edited) and `label_column` (the column of the resource's `label_field`, nil for none) are facts of the person's model, set by `for_actor/2` (stage 9c; with `authorize?: false` too) and kept in step with the columns by `supply/2`, which derives both again from the columns as they are (after `Live.Core.in_words/1`; every model the core puts into a table goes through it, `Core.Reading.settle/4`); kits compare columns with it by `name`. `zoned/2` puts the page's time zone into the model (`time_zone`) and its arguments.
- `Model.Column`, `Model.Field`, `Model.Input`, `Model.Action`, `Model.Argument`, `Model.Relationship`, `Model.Pagination`: structs. Each file starts with a comment that explains every key. `Pagination.size/2` is how many records a page holds for the size a person asked for: one of `page_sizes`, else `page_size`. `Field.from/1` makes fields of what `Resource.Embedding` gives, which are maps; `Field.of/2` the fields and kinds of a type, `Field.undeclared/1` what a map that declares none holds, by its keys in words. A column's `takes` says what each of its `operators` takes. `Column.value/2` is what a record holds for a column. `Argument.argument_id/1` is what an argument is called in the page, `Argument.shown/3` what its input shows.
- `Model.Limits`: `min`, `max`, `step` and the text counter. `of/2`, `counted/2`.
- `Model.Access`: what Ash says the person may see and do, before any read. `hidden_fields/4`, `partly_hidden_fields/4`, `forbidden_actions/3`.

State and URL:

- `AshDataTable.Caller` (`caller.ex`, 2a): who is asking and what the page adds: `scope`, `actor`, `tenant`, `time_zone`, and the page's `context`, `private_arguments`, `page_arguments` (maps or functions), `before_action` and `notify` (which events the page is told) (stage 6). No assigns. `new/1`; `reader_opts/1` is the keyword list the functions of 2a take as `opts` (`actor`, `scope`, `tenant`); `Live.Core.reader/1` adds the entry's `authorize?` (as told, else the domain's), puts the table's listener (`origin`) in front and, given the socket, `page_values` (`Live.Core.values/1`).
- `AshDataTable.State` (`state.ex`): sort, filters, arguments, page position, chosen page size (`per`). `from_params/2` and `to_params/2` are the URL format. `fit/2` drops what the model does not allow. `cycle_sort/3`, `filter/3`, `pending/2` (what the filter row was sent, an operator without its value among it), `value?/2`, `clear_filter/2`, `clear_filters/1`, `argue/3`, `put_argument/4`, `to_page/2`, `resize/3`.
- `AshDataTable.Related` (`related.ex`): the URL parameter `of` that limits a table to the records of one row (the full view). `from_params/5`, `to_param/2`, `path/5`.
- `AshDataTable.Routes` (`routes.ex`): where the host's router mounts a table. `default_id/2`, `table/4`.

Reads:

- `AshDataTable.Query` (`query.ex`): every read through the table's read action. `read/3` (one page), `read_related/4` (a nested table), `get/5` (one record by key), `matching/3` and `records/3` (a selection), `related_records/5`, `load/3`, `arguments/2`, `rows/4` and `any?/5` (live updates), `summaries/4` (footer summaries: one `Ash.aggregate/3` over everything that matches). Returns `%Query.Page{}`. `reader_opts/1` makes the Ash options of `opts` (idempotent): who asks, `authorize?`, and the `context` of `page_values` with the table's own key (`ash_data_table_origin`) last. `private/3` and `action_opts/3` are the private arguments an action declares, of `page_values`; `privately/3` sets them on a read. Every function of 2a takes `opts` with `page_values` and reduces them where it calls Ash.
- `AshDataTable.Record` (`record.ex`): the record of one row, read again as the person. `fetch/3`, `key/2`, `load/3`.
- `AshDataTable.Pick` (`pick.ex`): the record a person chose in the picker. `chosen/3`, `current/3`, `value/2`, `reader/2`.

The live core (2b):

- `AshDataTable.Live.Core` (`live/core.ex`) and its modules `Core.Reading`, `.Url`, `.Nesting`, `.Updates`, `.Cells`, `.Picker`, `.Panel`, `.Bulk`, `.Files`, `.Opener` with `.Opener.Table` and `.Opener.Host` (`live/core/`, `live/core/opener/`): socket in, socket out; what the callbacks of the tag's component and the hooks of an attached table do. See "The wiring and the live core" below.

The state of a table (2b):

- `AshDataTable.Table` (`live/table.ex`): the one value a table is held in, under the attach name (the tag's component and the page use `table`); public, opaque (moduledoc only; a host reads it with `AshDataTable.status/1`): `options` (what the table on the page was told about how it is placed: `url`, `heading`, `mounted?`, `page_assigns` (a map, or `:socket` for an attached table: `Live.Core.page_assigns/1` gives the host's assigns), `target` (the tag's `@myself`, nil when attached: the parts' `phx-target`, and how a listener relays), `router`, `controlled` (what the host draws itself, `attach/4` only; for every table the table shows, nested tables and pickers' tables too), `kit` (the module it is drawn with), `presentation` (what opens in the page or over it, `panel: :inline`, over what its kit says), `look` (`Kit.look!/2`, over what its kit says; every table it shows looks the same)), `caller`, `entry` (the table on the page), `entries` (every other table it shows, by id: nested tables at every depth and the tables of open pickers), `pool` (stream names, `ID:rows`, `ID:rows_1`, … after the id of the table on the page) and `models` (the models `Model.build/2` gives, the same for everybody, by all they are built of: resource, table, `via`, the read action of a table to choose from, `live?`; one per kind for the whole tree, so the nested tables of one relationship share one; not kept where the endpoint reloads code; `Core.Nesting.built/1`). `new/0`; `put/2` puts fields where each lives and raises on a name none has.
- `AshDataTable.Live.Registry` (`live/registry.ex`): the tables of one `Table`. `within/3` checks an entry out into `table.entry` for the live core and puts the table on the page back (outside it, `table.entry` is always the top's; a table other than the top is shown the options of a placed table: no URL, heading or page of its own); `known?/2`; `async/2` (the task keys `{:ash_data_table, id, {:read | :summary | :bulk, token}}`, the token the entry's own) and `current?/2` (an answer of a closed entry is dropped, also when an entry of the same id opened since); `finishing/1` (the function of every `start_async` task that runs a query, read, summary or bulk: it traps exits, so it finishes its query when the LiveView ends or its table closes, and its answer is dropped; no task is cancelled, #66); `take_stream/1` and `give_back/2` (the pool: `"ID:rows"`, `"ID:rows_1"`, …, each configured once); `add/3`, `close/2`, `close_all/1` (`detach/2`: every entry and the top's own) (its request ended, `Core.Opener.closed/2` of every kind; listener stopped, uploads cancelled and disallowed (its tasks are left to finish) (one whose file is on its way stays allowed until a table of the same id takes it again: LiveView refuses to give it up), stream emptied and back in the pool, entry gone); `portals/1` (the nested entries in the order they opened, the entry's `opened`: parents first, a new one last, so no portal moves for it).
- `AshDataTable.Live.Entry` (`live/entry.ex`): one table: everything else it holds, each field with its comment (see "The state of a table" below). `new/0`.

Live updates:

- `AshDataTable.Resource.Notifier` (`resource/notifier.ex`, part 1): the Ash notifier of a resource that says `live? true`. Broadcasts `{:ash_data_table_changed, resource, action_type, primary_key, tenant}` and nothing else. `topic/2` is the topic of a resource and a tenant.
- `AshDataTable.Listener` (`live/listener.ex`, 2b): the process through which one table hears. `start/3` subscribes and hands batches (100 ms) to the table: `send_update` to the tag's component, or `{:ash_data_table_heard, id, batch}` to the LiveView of an attached table; `stop/1`; `flush/1` and `of/1` for tests. It ends with the LiveView.
- `AshDataTable.KitCase` (`kit_case.ex`, T, public): `use AshDataTable.KitCase, kit: Mod, endpoint: Endpoint` defines a probe kit (`TEST.Probe`) that draws every part through `Mod` after checking the part's assigns against its projection (`given!/2`: every key of `Kit.Projection.keys/1` and nothing beside but `kit`, `id`, a row's item or a cell's, the stream, the panel's uploads, the root's slots and a `class`; wherever the projection shows words, each message a map `%{key:, values:}` of a key of `AshDataTable.Messages` with exactly its values, an action's the key `:ash` with `message` and `vars`, its text beside it), and generates a test per state (`states/0`, 20: rows, filtered (with the panel of a filter's values on the way), empty, error, loading, nested, failed, secret_failed, panel, rekey, create, create_failed, list_panel, map_panel, groups_panel, staff, staff_picker, picker, selected (one row selected, said by the server, on the way), links) and per presentation (`presentations/0`: modal, inline, mixed (panel and picker modal, question inline), inside (panel modal, picker and question inline: a field's picker is drawn inside the panel)). Each mounts `AshDataTable.KitCase.Live` (`live_isolated/3`), which attaches a table of `AshDataTable.Test.Resource` (id `kit`) in a tenant of the test's own (`given/4`, public, seeds a state's records and gives the tenant, the first key and the session of `KitCase.Live` (public); `clean/1`, public, stops its ETS tables; `test/kit/kit_case_seeds_test.exs`), drives it with `AshDataTable.Test.send_event/5` and `send_form/5`, and asserts on every page on the way (`AshDataTable.Test.page/1`, `LazyHTML`) the markers, the ids of stage 7a's list and every server-written `data-*` value the hooks read (`grep -rhoE 'dataset\.[a-zA-Z]+' assets/js`; `pending` and `presentation`'s are the hook's and the part's own), the element kinds (the constants of D3 b on every cell, header, row and record; a modal part a `<dialog>`, an inline one `role=region`, and inside a modal panel or picker the question's place where questions are inline; one control per editor template, none for a list's), the stop rule of stage 8a K1 (`role=table`, `cell`, the label column's `rowheader`; an editable cell `tabindex="0"` (each cell of the record, all editable, and the nested table's `title`), a read-only cell none (the nested table's `secret`), no other cell, header or control with a `tabindex`; a failed cell described by its message only; a sort button in each header that sorts and in no other; the skip link before the header row and its target after the pagination, top, nested and in the picker; no `aria-readonly`, `aria-selected`, `aria-multiselectable`, no `aria-invalid` on a cell), that every part is drawn once (`related` and `full_view`, which need a router, with `render_component/2` in the state `links`), and that the page holds no `Test.Resource.secret/0`. The root suite runs it against `Kit.Default` (`test/kit/default_kit_test.exs`, on `AshDataTable.Test.LiveHost.Endpoint`, stage 9a), the demo against `DemoWeb.DivKit` (`demo/test/demo_web/kits/`). `client: true` (stage 8 R4, a kit that draws in the browser, `DemoWeb.ReactKit`): the texts contract and the secret check only (the props and the stream's items are in the page's HTML), the events from the grid's sender (`Attrs.sender/1`), a form as its event; `problems/4` runs the marker checks over a page's HTML as the browser drew it (`demo/e2e/kit_check.spec.ts` through `/e2e/kit/check`; `:row_selected` beside the states, the hooks' elements without `phx-hook`).
- `AshDataTable.Test.Resource` (`test/resource.ex`, T, public): the resource `KitCase` draws, in memory (`Ash.DataLayer.Ets`, `multitenancy :context`), with its domain, `Owner` (the pickers' table: a primary key that is no DOM id, so its rows say `data-key`; a sensitive `pin`) and `Part` (the nested table: no label field, a sensitive `secret`): a column of every kind (text with `max_lines` and `confirm`, `sensitive?` with `confirm`, boolean, a component with a `summary`, one of two values, a list, a map, a list of maps, a union, a reference with `confirm`), the label column kept in view (`sticky_label? true`), a read argument, row actions with a file (`stamp`), with the sensitive field and the list (`rekey`), with helpers chosen in the picker (`staff`), one that asks and runs on a selection (`destroy`), a table action that asks (`greet`), create. A read in a tenant that begins with `broken` fails. It uses the extension as a host's resource does: `test/architecture_test.exs` lets it be compile-connected.
- `AshDataTable.Test` (`test.ex`): public help for a host's tests. `flush/1` hands a page what was announced so far; `listening/2` counts listeners (each `Listener` puts its `{pub_sub, topic}` in its process dictionary; `Process.list/0` and `Process.info/2` find them, not PubSub's storage). For nested tables and pickers, which `Phoenix.LiveViewTest` does not see inside a portal: `page/1` (the page as the browser shows it, a `LazyHTML`), `send_event/5` (a table's event by its name, through the component that draws it, or the LiveView it is attached to), `send_form/5` (a form as the browser sends it, inside a portal too), `table_named/1` (the table an event's name is for). `DemoWeb.TablePage` calls them.
- In `AshDataTable.Query`: `rows/4` reads announced keys again as rows are read, `any?/5` asks whether one of them is the person's to see under their filters. `reader_opts/1` passes a table's own listener on as `context` (`origin`), so that the notifier leaves it out.

Writes:

- `AshDataTable.Operation` (`operation.ex`): the one way a table writes. `save/1`, `clear/1`, `refer/1`, `reveal/1` (the one way to a sensitive value), `run/1` (a row or table action without a panel), `submit/1` (the open panel: what `Panel.submission/2` says it runs, `{:submit_cell, …}`, `{:submit_row, …}`, `{:submit_table, …}`, `{:submit_create, …}`, `{:submit_bulk, …}`, each with what the panel holds of it: `params`, `form`, `inputs`, `time_zone`, `cleared`, `picked_with`; the kind is not matched here), `bulk/1` (a selection without a panel), `link/2` (what a nested table's create is given of its row). What the browser names is looked up here only, by its name as text: `column/2`, `action/2`, `table_action/2`, `bulk_action/2`; the live core asks these too. Each takes an `Operation.Input` (the intent, model, state, `parent`, `opts`, `picking`, `rows`, `selection`, `read?`, `offered`, `with_files`, `veto`, `page_values`) and runs, in this order, the checks of what the browser named, the veto (a function of an `AshDataTable.Request`, made by `Live.Core.veto/1`), the files, the re-read and the action, given `page_values`. ## The wiring and the live core

The drawing is `AshDataTable.attached/1` (the five colocated hooks, four lines each, which import the hooks of `assets/js/`) and `AshDataTable.Live.Drawing` (`lib/ash_data_table/live/drawing.ex`, part 4): `drawn/1` (the table on the page, then one portal per nested table) and `body/1` (the parts of one table, in their order, each through the table's kit, `options.kit`, inside the kit's `root/1`, which draws the table's root element (`Attrs.root/2`, the kit's `class(:root, …)`; `nested?` for a nested table and a picker's): the question, the panel and the picker in its slot `opened`, the panel and the picker drawn always, nil while closed; a picker a field of a modal panel opened, where the picker is inline, and the question's copy where questions are inline, moved by a portal into the panel's place, `Ids.panel_place/1`, and the picker's table and its question's copy into the picker's, `Ids.picker_place/1` (contract 5)). Each part is given its projection an attribute per key (`Projection.of({part, key}, inputs)`, each key of the inputs it depends on; stage 9f), never as a spread, which turns LiveView's change tracking off for the part (and LiveReact, which reads its props' changes from LiveView's, stops updating); the related line and the panel are made whole once (`whole/1`). Every part but the root (whose slots it draws) and the message (a comprehension of its own) is given its keys out of a comprehension of one (`:for={projection <- [%{key: Projection.of({part, key}, …), …}]}`): LiveView compares each key with what it was, as it does a comprehension's variables, so a part sends again only what changed of a key, and LiveReact, given the old value, sends a patch of an island's prop, not the prop whole. The markup contract (ids, `aria-colindex`, components) and one section per feature is the long comment at the top of `lib/ash_data_table/attrs.ex`; read the section of the feature you touch. The callbacks are `Live.Embedded`'s (the tag) and the hooks of `Live.Hooks` (an attached table, the page); each hands the socket to the live core.

The logic is `AshDataTable.Live.Core` (2b), one module per topic (`lib/ash_data_table/live/core.ex`, `core/*.ex`; who draws what opens is `Core.Opener`, which the topics ask, with its adapters in `core/opener/`). ### Events

Every event is named with the table it is for: `ash_data_table:ID:event` (target.md Q4). The markup names it with `Attrs.event/2`; a hook sends the plain name, and its transport (`assets/js/transport/live_view.js`) names it with the id of the hook's element. All arrive in `Live.Core.handle_event/3`, which splits the name at its first and last `:` (`addressed/2`), parses the event once with `AshDataTable.Intent.parse/2` and hands the intent to `on/2` of its topic's module (`topic/1`): `{:sort, column}`, `{:save, row, column, typed}`, `{:bulk, action}` (the selection is the entry's), …. A payload of another shape, and an event named for another table or without the prefix, gets the answer `malformed/2` gives for that event, the one the table always gave it (`{ok: false}`, `{open: false}`, `{}` or none); an event the table does not know has no clause. A name from the browser is looked up as text (`Operation.column/2`, `Operation.action/2`, …); it is never turned into an atom. Every write (`save`, `clear`, `reveal`, `act` without a panel, `table_act`/`table_run` without a panel, `bulk_run`, `panel_submit`, and `picked` for a reference cell) goes through `AshDataTable.Operation`, which checks the claims; opening a panel or a picker is a read and stays in the live core.

- Reading: `sort`, `filter`, `clear_filter`, `clear_filters`, `filter_values` (the button of a filter for several values: `{column, operator}`, opens the side panel), `page`, `page_size`.
- Argument line: `arguments`, `argument_add`, `argument_remove`.
- Nested tables: `expand`, `toggle`.
- Cells: `save` (one text), `clear`, `discard`, `dismiss`, `reveal` (sensitive), `edit` (a cell of several values, opens the panel).
- Row actions and create: `act`, `create`; `open` (the page's "Open" of a row: `Core.Panel` tells the page `:row_opened`, whatever `notify` says).
- Table actions: `table_act`, `table_run`.
- Selection: `select` (every change of what is selected), `bulk`, `bulk_run` (the action and the token of the selection its question named: the selection is the entry's, and runs only while it is the one named), `bulk_seen`.
- Action panel: `panel_validate`, `panel_submit` (the form; of a filter's panel, the filter), `panel_add`, `panel_remove`, `panel_unpick`, `panel_clear` (its buttons, `phx-click`: the server says where focus goes, `ash_data_table:focus`), `panel_cancel`.
- Picker: `pick` (from a cell), `pick_input` (from the panel), `picked` (`{confirmed, arguments}` or `{none}`: the record is the one the picker's table holds as selected), `picker_cancel`.
- Live updates: `read_again` (the button beside the notice), `left` (the hook's answer to `ash_data_table:leaving`: no cell of that row is being edited, it can go). No event says which cell is edited: the hook alone knows, and it leaves that cell alone when a live update puts its row back.

A new event is a clause of `Intent.parse/2`, an `on/2` clause in the module of its topic, its tag in `Live.Core.topic/1`, and its name in `malformed/2`. The id in an event's name is looked up among the tables of the `Table` (`Registry.known?/2`; for an attached table first among the tables of the socket, `Live.Hooks`) and the intent runs within that entry (`Registry.within/3`); an unknown id gets `malformed/2`'s answer. `tidy/1` runs over every table shown: it reconciles (`Nesting.reconcile/1`), follows what was announced and the held rows of every table, parents first, reconciles again, puts a row's detail again where the count of an open nested table changed (`Nesting.counted/1`, the entry's `counts`, the detail item's `counts`), tells the opener of each table which panel and picker are open (`Opener.opened/3`, the panel first), and asks for the summaries that are due.

Each event's payload and answer, and what sends it, are listed in the moduledoc of `AshDataTable.Attrs` ("Events", made of its `@events`; public since stage 8 R0, for a kit that draws in the browser). The server tells the hooks with `push_event`, whose names carry no table id: `ash_data_table:focus` (the grid's hook and, after a button of the panel, the panel's), `ash_data_table:ask`, `ash_data_table:select` (what is selected, where the server decided it), `ash_data_table:leaving` (a row whose record a live update found gone), `ash_data_table:answered` (controlled mode: a save, clear or reference cell's choice that waited for the host's answer to its column's question, by the request's `ref`, which the reply `{held: true, ref}` gave the hook; the hook keeps the cell busy by that `ref`, showing what the question is about (what was typed) across patches of its row in every kit (`waitFor`, `rehold`: a patch's content is kept aside), and puts it back as it was, or as the last patch brought it, as the answer comes; an answer to a `ref` it holds no more touches nothing), each with `table: id`. The hooks tell each other with DOM events on the grid: `ash_data_table:selection`, `ash_data_table:choose`.

### The state of a table

The table is one assign (`AshDataTable.Table`): `table` in the tag's component and the page, the attach name otherwise, beside LiveView's (`streams`, `uploads`). The live core reads it with `Core.table(socket).entry.model` (or `.options.url`, `.caller.time_zone`) and changes it with `Core.put(socket, field: value)`; a function head says what it is for with the guards of `AshDataTable.Live.Current` (`when is_map(Current.entry(socket, :panel))`). `body/1` passes each part the fields it draws from, one attribute each, so LiveView's change tracking compares each field on its own: a change of one field renders again only what uses it (measured in stage 2: the bytes per action of `demo/perf/baseline.mjs` did not change). What lives where:

- Given by the caller (`update/2`): `id`, `resource`, `table`, `scope`, `actor`, `tenant`, `authorize?`, `live?` (kept as `live_given`), `url`, `label`, `heading`, `mounted?`, `select`, `choose`, `page_assigns`, `context`, `private_arguments`, `page_arguments`, `before_action`, `notify`, `open` (kept as `open_label`, the table on the page's only), `controlled`, `time_zone` (checked, nil is `"Etc/UTC"`; passed on to nested tables and pickers, and kept in an open panel); for a nested table `via`, `parent_key`, `parent_authorize?`, `parent_arguments`, `depth`, `depth_limit`, and for a nested table and a picker `path` (the path of the table it is in; the entry's `path` is it with its own id last). `scope`, `actor`, `tenant`, `time_zone`, `context`, `private_arguments`, `page_arguments`, `before_action` and `notify` go into `caller`; `url`, `heading`, `mounted?`, `page_assigns` and `controlled` into `options`; everything else, here and below, is a field of `entry` (`label`, `labelledby`, `select`, `live_given`, `authorize_given`, the resolved `authorize?`, `stream`, `uploads`, `target`, `given` among them). A nested table is told this by the table it is in, as `Nesting.reconcile/1` opens it, and again only when it changes (`given`).
- `live`, `waiting`, `held`, `notice?`: live updates. `live` is the table's listener and topic, nil for a table that does not follow. `leaving` are the rows that go once the hook answers. What is open under a table's rows is read from the registry (`Updates.working/1`, by `path`); the held rows of every table are looked at again after every callback (`tidy/1`). The listener relays `{:heard, id, batch}` to the tag's component, or `{:ash_data_table_heard, id, batch}` to the LiveView, which hands it to the entry `id`.
- `model`: the model for this person, made on every update from the one `Table.models` keeps (`Nesting.built/1`); its `editing?` and `label_column` are `for_actor/2`'s.
- `geometry`: where the columns and rows stand (`AshDataTable.Geometry`), made with the model and `selecting` (stage 9c; nil before the first update).
- `state`: the `%AshDataTable.State{}`. `read`: what the last read was of; a read runs only when this changes.
- `page`, `row_count`, `busy?`, `loading?`, `error`, `gone?`. Every message the entry holds is a message term (`error`, `fill`, `announcement`, a failed cell's or row's message in `failed`, the panel's `title`, `submit`, `question` and `errors`, the picker's `title` and `error`, a run's `result`): the parts say it as they draw it.
- `counts`: by row key and relationship, how many records each open nested table has, where it has read and knows it (`Nesting.counted/1`); its line says it.
- `rows`: by the key in a row's DOM id, the primary key and row index. An event names a row by that key, and it is looked up here.
- `failed`: edits that failed, by row: what was typed and the message, never the record; Escape on a failed cell (`discard`) or actions cell (`dismiss`) reads the row again as the person (`Reading.put_read/2`, through `Query.rows/4`). `open`: expanded rows.
- `missing`, `fill`, `refused`, `lines`: the argument line.
- `rejected`, `pending`: what the filter row shows beside the filters of the state: a value that was typed and is none, and the operators that were chosen without a value yet (`shown_filter/4`).
- `panel`, `picker`: the open action panel (`AshDataTable.Panel`, put and taken out by `Core.Panel` only, with the entries of its uploads an action was given, `spent`) and picker, or nil. `request`: in controlled mode, the question or panel the host draws (`ref`, `kind`, `for`: what it was made for), nil for none (`Core.Opener.Host`'s only).
- `selecting`, `selected`, `all?`, `selected_under`, `bulk`, `running` (`action`, `by`), `result`: selection and its actions. `selected` are the rows as the hook names them (primary keys, claims) or `all?`, held on the server (`Core.Selection`); `selected_under` what they were selected under. `Operation.Input.selection` is made of them.
- `uploads`: the names of the uploads the table allowed.
- `summary`, `summing?`, `summed`, `summary_due`: footer summaries (whether there is a footer row is `geometry.summary?`). `summary` holds by column `{:ok, value}` or `:unavailable`; `summary_due` (`:changed` after a read, `:force` after a write or a live batch) is answered in `tidy/1` by `summarise/1`.

### Async reads and the stream

- `start_async(:read, …)` in `Core.Reading.read/1`. The first read of a table on the page runs in place, so the first render has rows. Later reads, and every read of a nested table, run async with `busy?` set.
- `start_async(:bulk, …)` in `Core.Bulk.start_bulk`, with the run `Operation.bulk/1` or `Operation.submit/1` hands back (`AshDataTable.Bulk.run/5`). Its outcome holds message terms; `Core.Bulk.handle_async(:bulk, …)` keeps them, each text once (`Text.counted/1`), and the part says them in this process.
- `start_async(:summary, …)` in `Core.Reading.summarise/1`, which calls `AshDataTable.Query.summaries/4`: beside the read of the rows, never before them. `read/1`, `put_row`, `remove_row`, `add_row` and `follow` say that it is due (`due/2`); `tidy/1` starts it once.
- One stream per table, its name from the pool (`entry.stream`, `ID:rows`…), configured with `dom_id`. The names an id configured are kept on the socket across `detach/2`. An item is a plain map of `AshDataTable.Item` (stage 8 R0, ADR 0002): a row (`Reading.item/3`: `Present.row/3`, then `Item.row/3`, with each cell's text) or the detail under an expanded row (`Reading.detail/3`, `Item.detail/5`, `detail: true`). A new read resets it. `put_row` and `put_detail` insert one item; `remove_row` deletes a row and its detail. The server does not keep the records.

### Nested tables through portals

Every table a table on the page shows is in its one `Table` (stage 5); there is no live component but the tag's. `attached/1` draws the table on the page (`body/1`, the markup of a table, given its entry; the table of an open picker is drawn by `body/1` in a `<.portal>` into the picker's place, `Ids.picker_place/1`, and a picker inside a modal panel and the question's copy into the panel's, `Ids.panel_place/1`, each marked `data-ash-data-table-portal` with its place; the panel and picker parts are drawn always, nil while closed, contract 5) and after it one `<.portal>` per nested table (`Registry.portals/1`, in the order they opened, parents first; its wrapper takes the kit's `class(:portal, …)`, `contents` in `Kit.Default`), each with the two elements that pin and size it, marked `data-ash-data-table-portal` and `data-ash-data-table-view` and styled by those markers in the root's rules (`Parts.Grid.root/0`), and the nested table's `body/1`. LiveView moves each portal's content to the end of its target, the cell `ID-row-KEY-n-NAME-c` that `Parts.Related.lines` draws empty, in a wrapper of its own that the table relies on in no way. The rule that shows a line's buttons once its nested table has read (on the root, `Parts.Grid.root/0`) finds the nested table by the table's own marker (`[data-nested] [data-ash-data-table-portal] [data-read]`). Nothing in the portal loop reads `@table`, which changes with every table of the tree: `Drawing.portals/2` makes each portal's values (`{entry, rows, placed}`, `placed` the options, kit class, chooser and the like), which LiveView compares portal by portal, so an event of one table sends and patches only its own portal. LiveView keeps a nested table's last rows in its change tracking until the next render (a keyed comprehension's variables, the portal's stream among them); the table itself stores no rows. A portal must never outlive its cell: every change of `open`, `rows` or `picker` is reconciled in the same callback (`tidy/1`). `Phoenix.LiveViewTest` does not look into a portal: the outer pinning element names its cell (`data-ash-data-table-portal`), and `AshDataTable.Test.page/1` (with it `DemoWeb.TablePage`) and the markup snapshots put what it marks into that cell (the snapshots drop the emptied template, `ID-portal`).

### The footer row

A table with a `summary` on one of its columns has a footer group (`ID-foot`, a `<tfoot>` in the default markup) whose first row, `ID-summaries`, holds a `cell` per column (`ID-summary-FIELD`, no Tab stop); a nested table's pages and its link to the full view are the rows after it. ## Safety rules

Every change must keep these. They are what part 2 is for.

- **Read again as the person before any write.** The table keeps keys, not records. Before a save, an action, a reveal or a pick, the record is read again by its key through the table's read action, with the person's actor, tenant and arguments (`AshDataTable.Record.fetch/3`, `AshDataTable.Pick.chosen/3`), inside `AshDataTable.Operation`, after its checks and the veto. A record that read does not return is not there.
- **Every action a table runs is `public?`.** Read, update, create, destroy and generic actions, and the read action of a nested table or a picker. The verifiers refuse a private one (`Reading.read_action/2`, `Reading.private_read/2`, `Relating.public_read/2`, `Acting.unusable/4`; the sentence they share is `Reading.private_action/0`).
- **`authorize?`.** Every call to Ash passes the reader options (`scope`, `actor`, `tenant`, `authorize?`; `AshDataTable.Caller`, `Live.Core.reader/1`, `Query.reader_opts/1`). `authorize?` comes from the domain unless the table is told otherwise. The table adds no rule of its own and hides nothing by itself: it asks Ash (`Model.Access`).
- **Nothing sensitive reaches the browser before "Show".** A part draws only from what `AshDataTable.Present` gives: a row from a record that went through `AshDataTable.Sensitive.scrub/2`, a sensitive cell as `:masked` with no value, a sensitive field of the panel with only what was typed in it, the label of a chosen record scrubbed. `test/present_test.exs` checks it for every function. The value is sent only as the reply to `reveal`, after the record was read again (`Operation.reveal/1`). An editor of a sensitive column opens empty.
- **An announcement is a claim too.** A live update names a primary key and nothing else. The table shows only what its own read returns for that key, as the person (`Query.rows/4`), and says that there are new or changed records only after asking, as the person and with their filters, whether one is theirs to see (`Query.any?/5`). The notifier never sends a record.
- **A summary says no more than the rows.** `Query.summaries/4` asks `Ash.aggregate/3` with `authorize_fields?: true` and with the table's read action as each aggregate's `read_action` (Ash would otherwise judge field policies as the primary read action meets them), and asks for nothing over a column that is `partly_hidden?` for the person: its footer cell is a dash. `summary` is refused on a `sensitive?` column.
- **Values from the browser are claims.** A row key, a column name, an action name, a picked record and a selection are looked up or read again before they are used. A page size from a URL or an event is taken only when it is one of the table's `page_sizes` (`State`, and once more where the query is built: `Model.Pagination.size/2`). Sort and filter go through `Ash.Query.sort_input/2` and `Ash.Query.filter_input/2`. What a person typed goes to the action as typed (but a wall time of a datetime, which goes as the UTC instant it is in the page's zone: `AshDataTable.Zone`); Ash casts and validates it. Text from outside never becomes an atom.

The fixture `sandbox` (`demo/e2e/support/server.ts`, automatic) starts it with `POST /sandbox` and ends it with `DELETE /sandbox` once the test's browser contexts are closed (an answer other than 200 fails that test: its transaction was lost before it ended, #66); the fixture `userAgent` makes its metadata the user agent of every context and request of the test, `browser.newContext()` and `request` included, so the two people of a test share one transaction. The plug at the top of `DemoWeb.Endpoint` allows each request, and `DemoWeb.E2E.Sandbox` (`demo/e2e/server/sandbox.ex`, a child of the application) each connected LiveView, from the user agent of the socket's `connect_info`, as it hears LiveView's telemetry `[:phoenix, :live_view, :mount, :start]` (before the `on_mount` hooks; the router stays as a host writes it, which the guides quote); what a LiveView starts with `start_async` is allowed through `$callers`. Where the endpoint serves, the sandbox is in manual mode (also `DemoWeb.E2E.Sandbox`), so a process nobody allowed fails. Nothing is seeded after a test: a test that writes needs nothing said. `sandbox.spec.ts` checks that a write is its own test's and gone when it ends. A server per worker, not one for all: a transaction keeps a test's writes from the others, but not its row locks, the live updates its writes announce (PubSub is the server's), or the memos of `/e2e/controlled` (ETS); on a server of its own, a worker runs one test at a time.
- Single-server mode, for writing a test: `./server.sh` in `demo/e2e` serves the e2e environment on 4479, and `npm run test:server -- editing` runs against it, one test at a time, each in its own transaction as well.
- The Node version is the `nodejs` line of `demo/e2e/.tool-versions`.
- In development the demo has Tidewave, an MCP endpoint into the running app, at `http://127.0.0.1:4478/tidewave/mcp` (see `demo/README.md`).

Known traps:

- A file restored with the same modification time leaves a stale beam. After restoring a file, run `mix compile --force`.
- Never use `pkill -f` or `pgrep -f` with a pattern that matches your own command line. Stop a server by its process id.
- The dev server and the e2e servers write the asset bundle to the same path, `demo/priv/static/assets/`. A browser run rebuilds it.
- LiveView makes the `node_modules` link beside the extracted hooks once and keeps it. A `_build` from before the hooks moved has it pointing at `assets/node_modules`, and esbuild cannot resolve `../node_modules/js/index.js`: delete `_build/*/phoenix-colocated/ash_data_table/node_modules` (or `mix clean`), and the next compile makes it again.
- Tailwind scans `lib/` (the host's `@source` line), not `assets/js/`. A class the hooks set must also be written in the markup of `lib/`.
- A folder `demo/assets/react/` would shadow the `react` package (`demo/assets/tsconfig.json` has `baseUrl: "."`, which esbuild honours): the React components are in `demo/assets/islands/`.
- shadcn's raw variables are renamed `--sh-*`: daisyUI's `--border` is a width, shadcn's a colour. A Radix portal leaves `.shadcn`; its portalled element carries the class.

## Build rules (agreed 2026-10-13)

- Mutation checks only where a missed bug is dangerous: authorization, what is sent to the browser, and what gets written. Not for looks and convenience.
- Each suite runs once: root, demo, browser; a step runs only what it changed (`mix test --stale`, `--only-changed`, see "Running things"). A failure that passes on a second run is still looked into.
- A build writes only its own guide section. README, changelog and the other guides are caught up once per milestone.
