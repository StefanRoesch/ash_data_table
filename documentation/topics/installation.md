# Installation

The [tutorial](../tutorials/get-started-with-ash-data-table.md) installs the
library with Igniter in one command. This guide says what that command
changes, how to take the same steps by hand, and one setting the installer
leaves to you: compression of LiveView's websocket.

## Requirements

| Requirement | Version |
| --- | --- |
| Elixir | 1.17 or later |
| Ash | 3.36.1 or later |
| `ash_phoenix` | 2.3 or later |
| Phoenix | 1.8 |
| Phoenix LiveView | 1.2.12 or later |
| Gettext | 0.26 or 1.x |

The default kit draws the table with the Tailwind 4 and daisyUI classes of a
new Phoenix 1.8 app. A [kit of your own](kits.md) can draw it with anything
else.

An app generated by an older Phoenix 1.8 installer asks for
`{:phoenix_live_view, "~> 1.1.0"}`. Change that to `"~> 1.2"` in its
`mix.exs` first, or the dependencies do not resolve.

## With the installer

<!-- sketch -->
```sh
mix igniter.install ash_data_table@github:StefanRoesch/ash_data_table
```

Once the package is on Hex this is `mix igniter.install ash_data_table`. For a
checkout, `ash_data_table@path:../ash_data_table`. With the dependency
already in `mix.exs` and [Igniter](https://hexdocs.pm/igniter) among your
dependencies, `mix ash_data_table.install` does the same.

Each step is taken only if it has not been taken, so the task can run again.

| File | What the installer does |
| --- | --- |
| `mix.exs` | Adds the dependency (this part is `igniter.install` itself). |
| `.formatter.exs` | Adds `:ash_data_table` to `import_deps`, so that `mix format` leaves the `table` block without parentheses. |
| `config/config.exs` | Puts `table` and `tables` first in Spark's section order of a resource, and `table` of a domain, as other Ash extensions do. |
| `assets/js/app.js` | Imports the table's hooks and spreads them into the `hooks` of your `LiveSocket`. |
| `assets/css/app.css` | Adds an `@source` line, so that Tailwind sees the classes the table uses. |
| `config/config.exs` | Sets `layout`, `gettext_backend` and `translate_error` under `config :ash_data_table`, each only when your app has what it names and the key is not set yet. |

A file that does not look like the one of a new Phoenix 1.8 app is left as it
is, and the step is printed for you to take by hand. At the end the task says
what only you can do: list the extension on a resource, and add a line to
the router.

## By hand

1. Add the dependency in `mix.exs`:

   <!-- sketch -->
   ```elixir
   {:ash_data_table, "~> 0.1"}
   ```

2. Register the table's hooks in `assets/js/app.js`. There are five (the
   grid, the pagination, the action panel, the picker and the grid's
   sender). They ship with the library as colocated hooks behind one import;
   there is nothing to install from npm. In the demo,
   [`demo/assets/js/app.js`](https://github.com/StefanRoesch/ash_data_table/blob/main/demo/assets/js/app.js):

   <!-- source: demo/assets/js/app.js -->
   ```js
   import {hooks as colocatedHooks} from "phoenix-colocated/demo"
   import {hooks as ashDataTableHooks} from "phoenix-colocated/ash_data_table"
   // ...
   const liveSocket = new LiveSocket("/live", Socket, {
     longPollFallbackMs: 2500,
     // ...
     hooks: {
       ...colocatedHooks,
       ...ashDataTableHooks,
       // ...
     },
   })
   ```

3. Let Tailwind see the classes the table uses, in `assets/css/app.css`:

   <!-- sketch -->
   ```css
   @source "../../deps/ash_data_table/lib";
   ```

   The path is the dependency's `lib` directory, seen from `assets/css`. For
   a path dependency that is the checkout, not `deps`: the demo depends on the
   library by path, and its line is `@source "../../../lib";`.

4. Add the DSL to the formatter in `.formatter.exs`:

   <!-- sketch -->
   ```elixir
   [import_deps: [:ash_data_table, :ash, :phoenix]]
   ```

5. Tell the table about your app, in `config/config.exs`. The demo's
   [`demo/config/config.exs`](https://github.com/StefanRoesch/ash_data_table/blob/main/demo/config/config.exs):

   <!-- source: demo/config/config.exs -->
   ```elixir
   config :ash_data_table,
     layout: {DemoWeb.Layouts, :app},
     gettext_backend: DemoWeb.Gettext,
     translate_error: {DemoWeb.CoreComponents, :translate_error}
   ```

   All three are optional and read while the app runs, so changing them
   needs no recompilation of the dependency.
   [Layout and embedding](layout-and-embedding.md) explains `layout`,
   [Messages and translations](messages-and-translations.md) the other two.
   A fourth key, `kit`, names the [kit](kits.md) every table is drawn with.

The hooks are written into your build directory when the dependency is
compiled, so `mix compile` has to run before the assets are built. The
`assets.build` alias of a new Phoenix app already does that.

## Compressing the websocket

A table sends much the same markup again and again: every row of a new page
has the same cells with the same attributes. Deflate compresses that well.
LiveView's websocket can compress its frames (permessage-deflate), and the
installer does **not** turn that on: it is a setting of your whole app, and
yours to decide.

To turn it on, add `compress: true` to the `websocket` options of the
LiveView socket in your endpoint. The demo does, in
[`demo/lib/demo_web/endpoint.ex`](https://github.com/StefanRoesch/ash_data_table/blob/main/demo/lib/demo_web/endpoint.ex):

<!-- source: demo/lib/demo_web/endpoint.ex -->
```elixir
socket "/live", Phoenix.LiveView.Socket,
  websocket: [compress: true, connect_info: @connect_info],
  longpoll: [connect_info: @connect_info]
```

**What it gains.** Measured on the demo's `/tasks`, a page change sends about
155 KB without compression and about 12 KB with it.

**What it costs.**

- **Memory per connection.** Each socket keeps a deflate state for each
  direction for as long as it is open.
- **CPU.** Every frame is compressed on the server and inflated in the
  browser, and the other way round.
- **A side channel.** When a secret and text an attacker controls are
  compressed in the same frame, the size of the frame can tell the attacker
  whether their text matches part of the secret, as the CRIME and BREACH
  attacks did on HTTPS. Weigh this where a page shows secrets (tokens, keys)
  next to text other people can write.

**Uploads.** A file sent through the socket is compressed too. Bandit, the
default web server of a new Phoenix app, refuses a frame that inflates to
more than 25 times its compressed size (`max_inflate_ratio`, a guard against
deflate bombs) and closes the socket. A real file rarely comes near that, but
a very repetitive one can (a CSV of thousands of identical lines). Leave the
guard at its default: raising it lets a tiny frame take a lot of memory.

## Edge cases

- **The installer without Igniter.** If Igniter is not among your
  dependencies, `mix ash_data_table.install` only prints how to get it and
  exits with an error. `mix igniter.install` needs the `igniter_new` archive
  (`mix archive.install hex igniter_new`).
- **No app layout, Gettext backend or error translator.** The installer sets
  no key for what your app does not have, and says so. Mounted tables are
  then rendered bare in the root layout, the tables speak English, and the
  messages of your actions are shown as the resource wrote them.
- **A Tailwind 3 app.** The installer finds no `@import "tailwindcss"`, and
  prints the step. Add the dependency's `lib` directory to `content` in
  `tailwind.config.js`.
- **Compression and long polling.** `compress: true` is a websocket option.
  A browser that falls back to long polling gets no compression.

## Things people trip over

- **`mix compile` before the assets.** An `esbuild` that runs before the
  dependency is compiled does not find `phoenix-colocated/ash_data_table`.
- **Restart the server after changing a path dependency.** The Phoenix code
  reloader does not recompile `{:ash_data_table, path: "…"}` and does not
  rebuild the hooks. Stop the server, run `mix assets.build`, start it again.
- **The table looks unstyled.** The `@source` line is missing or points at
  the wrong directory, so Tailwind never saw the table's classes.
- **Enter on a cell does nothing.** The hooks are imported but not spread into
  `hooks`, or the assets were built before the dependency was compiled.
- **An upload closes the socket.** Compression is on, and the file is very
  repetitive: see [Compressing the websocket](#compressing-the-websocket).

## Not in the first version

No installer step for a Tailwind 3 app, and the hooks are not published on
npm (they come with the Hex package). See
the [specification](https://github.com/StefanRoesch/ash_data_table/issues/21).
