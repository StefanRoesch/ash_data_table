# Get started with AshTable

At the end of this tutorial one of your resources is a page in your Phoenix
app: a table that people sort, filter and page through, with the columns you
chose, one column they can edit in place, and a save that the resource's
policy refuses for the wrong person. You write no HEEx for it.

Every step shows the code of the demo app in
[`demo/`](https://github.com/StefanRoesch/ash_table/tree/main/demo), an issue
tracker that ships with the library, and names the demo page where you can
see the step working. Do the same in your own app with your own resource.
[The demo's README](https://github.com/StefanRoesch/ash_table/blob/main/demo/README.md)
says how to start it; it then runs at `http://localhost:4478`, and the
"Acting as" switcher in the page header chooses who you are.

The code blocks are excerpts of the demo's files. A line that reads `# ...`
(`// ...` in JavaScript) stands for lines that are left out.

## Before you start

You need an existing Phoenix and Ash application with at least one resource.

| Requirement | Version |
| --- | --- |
| Elixir | 1.17 or later |
| Ash | 3.34 or later |
| `ash_phoenix` | 2.3 or later |
| Phoenix | 1.8 |
| Phoenix LiveView | 1.2.10 or later |

The table is styled with the Tailwind 4 and daisyUI classes of a default new
Phoenix 1.8 app, and its texts go through Gettext. The resource needs a
primary read action and at least one `public?` attribute. For the last step
it also needs an update action and a policy.

An app generated by an older Phoenix 1.8 installer asks for
`{:phoenix_live_view, "~> 1.1.0"}`. Change that to `"~> 1.2"` in your
`mix.exs` first, or the dependencies do not resolve.

## 1. Install

AshTable is not on Hex yet, so the installer is given the repository:

<!-- sketch -->
```sh
mix igniter.install ash_table@github:StefanRoesch/ash_table
```

Once the package is published this is `mix igniter.install ash_table`. With
the dependency already in `mix.exs` and
[Igniter](https://hexdocs.pm/igniter) among your dependencies,
`mix ash_table.install` does the same. The task can be run again: it takes
each step only if that step has not been taken.

| File | What the installer does |
| --- | --- |
| `mix.exs` | Adds the dependency (this part is `igniter.install` itself). |
| `.formatter.exs` | Adds `:ash_table` to `import_deps`, so that `mix format` leaves the `table` block without parentheses. |
| `assets/js/app.js` | Imports the table's hooks and spreads them into the `hooks` of your `LiveSocket`. |
| `assets/css/app.css` | Adds an `@source` line, so that Tailwind sees the classes the table uses. |
| `config/config.exs` | Sets `layout`, `gettext_backend` and `translate_error` under `config :ash_table`. |

The installer writes a configuration key only when your app has what the key
names (`MyAppWeb.Layouts.app/1`, `MyAppWeb.Gettext`,
`MyAppWeb.CoreComponents.translate_error/1`) and the key is not set yet. A
file that does not look like the one of a new Phoenix 1.8 app is left as it
is, and the step is printed for you to take by hand. The
[README](../../README.md#by-hand) lists the manual steps.

This is what the result looks like in the demo. The hooks, in
[`demo/assets/js/app.js`](https://github.com/StefanRoesch/ash_table/blob/main/demo/assets/js/app.js):

<!-- source: demo/assets/js/app.js -->
```js
import {hooks as colocatedHooks} from "phoenix-colocated/demo"
import {hooks as ashTableHooks} from "phoenix-colocated/ash_table"
// ...
const liveSocket = new LiveSocket("/live", Socket, {
  longPollFallbackMs: 2500,
  params: {_csrf_token: csrfToken},
  hooks: {...colocatedHooks, ...ashTableHooks},
})
```

The table has two hooks, one for the grid and one for the pagination. Both
ship with the library as colocated hooks behind the one import. There is
nothing to install from npm.

The configuration, in
[`demo/config/config.exs`](https://github.com/StefanRoesch/ash_table/blob/main/demo/config/config.exs):

<!-- source: demo/config/config.exs -->
```elixir
config :ash_table,
  layout: {DemoWeb.Layouts, :app},
  gettext_backend: DemoWeb.Gettext,
  translate_error: {DemoWeb.CoreComponents, :translate_error}
```

All three keys are optional.
[Layout and embedding](../topics/layout-and-embedding.md) explains the first,
[Messages and translations](../topics/messages-and-translations.md) the other
two.

The Tailwind source is the one line that differs from the demo, because the
demo depends on the library by path. For a package from Hex the installer
writes this line into `assets/css/app.css` (a sketch, not a line of the
demo):

<!-- sketch -->
```css
@source "../../deps/ash_table/lib";
```

The hooks are generated when the dependency is compiled, so `mix compile` has
to run before the assets are built. The `assets.build` alias of a new Phoenix
app already does that. Run `mix assets.build` now.

## 2. Give a resource a table

List the extension on the resource. This is all `Demo.Tracker.Project`
needs for its table, in
[`demo/lib/demo/tracker/project.ex`](https://github.com/StefanRoesch/ash_table/blob/main/demo/lib/demo/tracker/project.ex):

<!-- source: demo/lib/demo/tracker/project.ex -->
```elixir
defmodule Demo.Tracker.Project do
  # ...
  use Ash.Resource,
    otp_app: :demo,
    domain: Demo.Tracker,
    data_layer: AshPostgres.DataLayer,
    authorizers: [Ash.Policy.Authorizer],
    extensions: [AshTable.Resource],
    # The default sort of a table lives on its read action, on purpose.
    primary_read_warning?: false
```

A resource has a table only when it lists the extension. With no `table`
block the table shows the resource's public attributes, read through its
primary read action, and nothing can be edited. (The demo's projects do have
a block. It declares no column, so the columns are the ones described
here. What it adds is the rest: it switches on editing, declares two row
actions and a create button, and says what a project is called in the
tables of other resources. See step 5,
[Row actions and create](../topics/row-actions-and-create.md) and
[Columns and defaults](../topics/columns-and-defaults.md#reference-cells).)

## 3. Mount it in the router

Import `AshTable.Router` and add one line per table, inside the
`live_session` whose `on_mount` hooks assign who is logged in. From
[`demo/lib/demo_web/router.ex`](https://github.com/StefanRoesch/ash_table/blob/main/demo/lib/demo_web/router.ex):

<!-- source: demo/lib/demo_web/router.ex -->
```elixir
import AshTable.Router
# ...
scope "/", DemoWeb do
  pipe_through :browser
  # ...
  live_session :default, on_mount: [DemoWeb.Actor, DemoWeb.Locale] do
    # ...
    ash_table "/tasks", Demo.Tracker.Task
    ash_table "/projects", Demo.Tracker.Project
    # ...
  end
end
```

`ash_table/3` expands to a `live` route for a ready-made LiveView. The
resource is written in full: the alias of the surrounding `scope` is not
applied to it.

Open `/projects` in the demo as Ada Admin. The page shows the columns ID,
Name, Description, Status, Starts on, Budget and Inserted at, ten projects to
a page, sorted by name. A click on a column's heading sorts, the row under
the headings filters, and the arrow keys move from cell to cell. The page size and
the order are not the table's: they are the `default_limit` and the sort of
the primary read action.
[Reading, sorting and pagination](../topics/reading-sorting-and-pagination.md)
explains why.

The demo's projects go beyond this step: the marks at the start of the rows,
the last column "Actions" and the button "New project" come from the
resource's relationships and from its `table` block. They are the subject of
[Nested tables](../topics/nested-tables.md) and
[Row actions and create](../topics/row-actions-and-create.md).

The table reads as the person your `on_mount` hook put into the socket
assigns `current_user` and `current_tenant` (or `current_scope`). In the demo
that hook is `DemoWeb.Actor`. If your app uses other names, see
[Authorization](../topics/authorization.md).

## 4. Declare columns

The default columns rarely fit: they include the `id` and leave out every
calculation and aggregate. A `table` block with `column` entries says exactly
which columns the table has, in which order. Part of the block of
`Demo.Tracker.Task`, in
[`demo/lib/demo/tracker/task.ex`](https://github.com/StefanRoesch/ash_table/blob/main/demo/lib/demo/tracker/task.ex):

<!-- source: demo/lib/demo/tracker/task.ex -->
```elixir
table do
  # ...
  # text
  column :title

  # enums. A change of state asks first.
  column :status do
    label "State"
    confirm "Change the state of this task?"
  end
  # ...
  # an aggregate: sortable and filterable, never editable
  column :comment_count do
    label "Comments"
  end
  # ...
end
```

Once one `column` is declared, the table has the declared columns and no
others. `label` replaces the column's heading, which is otherwise the field's
name in words. `comment_count` is an aggregate: it is a column because the
block names it. Open `/tasks` in the demo to see the full block at work.
[Columns and defaults](../topics/columns-and-defaults.md) has the rules.

## 5. Switch on editing for a column

Nothing can be edited until the block names an update action. A column can
name its own. The priority of a task is edited through the action
`reprioritise`:

<!-- source: demo/lib/demo/tracker/task.ex -->
```elixir
# edited through an action of its own
column :priority do
  update_action :reprioritise
end
```

The action is an ordinary update action of the resource that accepts the
column's attribute:

<!-- source: demo/lib/demo/tracker/task.ex -->
```elixir
# Leaves a trace of its own, so that it can be told apart from `update`.
update :reprioritise do
  accept [:priority]
  change set_attribute(:internal_note, "Reprioritised")
end
```

On `/tasks`, as Ada Admin, move to a cell of the Priority column and press
Enter. A menu of the priorities opens; choose one and it is saved. The table
ran `reprioritise` on that task with one input, the priority, and shows the
row as the action returned it.

The demo's block also has `update_action :update` at the top, which makes
every column editable whose attribute the action `update` accepts.
[Inline editing](../topics/inline-editing.md) covers both levels, the editor
of each type and what a failed save looks like.

## 6. See a policy refuse a save

The table has no authorization rules of its own. It runs the action as the
person who is logged in, and the resource decides. The policy of the demo's
tasks for update actions:

<!-- source: demo/lib/demo/tracker/task.ex -->
```elixir
policy action_type([:update, :destroy]) do
  description """
  Admins may run every action and viewers none (actor only). A member may
  change only the tasks they are assigned to or reported (record-dependent).
  """

  forbid_if actor_attribute_equals(:role, :viewer)
  authorize_if actor_attribute_equals(:role, :admin)
  authorize_if expr(assignee_id == ^actor(:id) or reporter_id == ^actor(:id))
end
```

Switch the demo to Max Member and open `/tasks`.

1. Change the priority of a task. Unless the task happens to be assigned to
   Max or reported by him, the cell is marked in the error colour and says
   "You are not allowed to change this." Nothing is saved. Press Escape on
   the cell to get the saved value back.
2. Switch to Vera Viewer. No cell opens at all: a viewer can never run an
   update action, so the table offers her no editing.

The first case is refused when the cell is saved and the second before
anything is typed. The difference is whether the policy depends on the
record. [Authorization](../topics/authorization.md) explains it, together
with hidden columns and refused reads.

## Edge cases

- **The installer without Igniter.** If Igniter is not among your
  dependencies, `mix ash_table.install` only prints how to get it and exits
  with an error. `mix igniter.install` needs the `igniter_new` archive
  (`mix archive.install hex igniter_new`).
- **A path dependency.** For `{:ash_table, path: "../ash_table"}` the
  Tailwind source is the checkout's `lib` directory, seen from `assets/css`,
  and not a directory under `deps`. The installer writes the path of the
  dependency as it finds it. The demo is such an app: its line is
  `@source "../../../lib";`.
- **No app layout.** If your app has no `MyAppWeb.Layouts.app/1`, the
  installer sets no `layout` and says so. Mounted tables are then rendered
  bare in the root layout.
- **A resource without a primary read action** has no table until the block
  names one with `read_action`. The compiler reports it: see
  [Mistakes at compile time](../topics/mistakes-at-compile-time.md).

## Things people trip over

- **`mix compile` before the assets.** An `esbuild` that runs before the
  dependency is compiled does not find `phoenix-colocated/ash_table`.
- **Restart the server after changing a path dependency.** The Phoenix code
  reloader does not recompile `{:ash_table, path: "…"}` and does not rebuild
  the hooks. Stop the server, run `mix assets.build`, start it again.
- **The table looks unstyled.** The `@source` line is missing or points at
  the wrong directory, so Tailwind never saw the table's classes.
- **The arrow keys do nothing.** The hooks are imported but not spread into
  `hooks`, or the assets were built before the dependency was compiled.
- **Nobody is logged in.** A table mounted outside the `live_session` that
  assigns the user reads as nobody. With a policy that filters, that is an
  empty table and not an error.
